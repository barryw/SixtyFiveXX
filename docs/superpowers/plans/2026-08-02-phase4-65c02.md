# Phase 4 — The 65C02 Family Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take the engine from one certified core to four — `Synertek65C02`, `Rockwell65C02` and `Wdc65C02` alongside the existing `Mos6502` — each certified against its own 2,560,000 Harte vectors, with the 6502 unchanged throughout.

**Architecture:** Phase 3 made the variant a compile-time type parameter. This phase uses it: a second opcode table, a shared CMOS baseline with two additive sub-variant deltas, and the handful of *behavioural* deltas that are not expressible as table rows. The tick loop stays monomorphic — no runtime variant branch in `Tick`/`Execute`.

**Tech Stack:** C# / .NET (`net8.0;net10.0`), xUnit, generic struct type parameters with static abstract interface members.

**Spec:** `docs/superpowers/specs/2026-08-02-variant-cores-design.md` §"Phase 4"

## Global Constraints

- **The 6502 must not change.** Every existing suite stays green throughout: 2,560,000 Harte vectors, Klaus functional, Klaus interrupt, the full unit suite, and the packed-surface test — on **both** `net8.0` and `net10.0`. A 6502 regression is never acceptable as a side effect of adding a variant.
- **The Harte vectors are the oracle, not a datasheet.** Where a cycle count, a flag, or a bus access is in doubt, the vectors decide. Do not hand-derive timing from a datasheet and then bend the vectors to fit; if a vector disagrees with your reading of the hardware, the vector wins and the reading was wrong.
- **No runtime variant branch on the per-cycle path.** If a variant check cannot be resolved at compile time or folded into table data, that is a design problem to report, not to paper over with an `if` in `Tick`.
- `src/SixtyFiveXX` keeps **zero** NuGet dependencies. `TreatWarningsAsErrors` is on; every public member needs an XML doc comment (CS1591 will fail the build otherwise).
- **The core invariant holds:** one `Tick()` = one clock cycle = at most one bus access.
- The 65816 is out of scope. The 6510 is phase 5. Do not anticipate either.
- Conventional Commits. Do not create tags or run `cog bump`. **Do not push to `main`** — a push to `main` without `[skip ci]` cuts a public nuget.org release.
- Work on a branch off `main`.

## Established facts — verified this session, do not re-derive

- **The three Harte 65C02 sets exist** at `raw.githubusercontent.com/SingleStepTests/65x02/main/{wdc65c02,rockwell65c02,synertek65c02}/v1/{00..ff}.json` — all three confirmed reachable, same JSON shape `HarteCache` already consumes. `HarteCache.Load(set, opcode)` **already takes the set name as a parameter**; no change is needed there.
- **Klaus's 65C02 extended binary exists** at `.../bin_files/65C02_extended_opcodes_test.bin`, confirmed **65,536 bytes** — the size `KlausCache.Load` already asserts.
- **Vector volume is the operational constraint.** The 6502 set alone is **1.0 GB** cached (256 files, ~4–5 MB each). Three more sets take the total to **~4–5 GB**. CI has no cache step and no volume today, so it re-downloads on every run. `HarteCache.Root` already honours `SIXTYFIVEXX_HARTE_DIR` — that is the hook Task 7 uses.
- **`MicroOpTable`'s private constructor takes only `OpcodeInfo[]`.** It hardcodes one IRQ/BRK/Reset micro-op sequence for every variant (`MicroOpTable.cs:64-107`). CMOS's interrupt deltas live in that shared sequence construction, not in per-opcode data. `OpcodeTableFor` already has the `CpuVariant` value one line earlier and does not pass it. **This is the known pinch point; Task 1 is exactly this.**
- **The CMOS interrupt change was anticipated in code.** `Cpu.cs:671-674` (`PushPBrk`) notes that keeping the hijack decision inside the P-push micro-op lets a CMOS table emit a different one without touching `Tick`, `VectorLo`, or the sequence layout. Follow that design rather than inventing another.
- **`Op`** (`src/SixtyFiveXX/Op.cs`) has no CMOS members. **`AddrMode`** (`src/SixtyFiveXX/AddrMode.cs`) has no `(zp)`, no `(abs,X)`, and no zero-page-relative mode. Both are `internal enum : byte`.
- **`Harte6502Tests` is hardcoded** to `Cpu<HarteBus, Mos6502Variant>`, the literal set name `"6502"`, and `Opcodes6502.Table` (for its JAM special case and its coverage assertion). It is not reusable as written — Task 2.
- **`PublicSurfaceTests` asserts an *exact* public type set.** Adding a public variant struct **will fail it by design**. The correct response is to add the new type to `ExpectedPublicTypes` deliberately, never to loosen the assertion.
- **`Irq_DoesNotClearDecimalModeOnNmos`** (`tests/SixtyFiveXX.Tests/InterruptTests.cs:72`) pins the NMOS behaviour that CMOS inverts. Both must be true simultaneously, per variant. Do not edit or weaken this test.
- The 65C02 has **no JAM opcodes** — every undefined NMOS opcode becomes a NOP with a per-opcode timing that is *not* uniformly one cycle.

## CMOS deltas, for reference

**Shared by all three sub-variants:**
- New opcodes/modes: `STZ`, `PHX`/`PLX`/`PHY`/`PLY`, `BRA`, `TRB`/`TSB`, `(zp)` indirect, `BIT` immediate and indexed, `INC`/`DEC` accumulator, `JMP (abs,X)`.
- `JMP ($xxFF)` page-wrap bug **fixed**.
- `D` **cleared** on interrupt entry (NMOS leaves it).
- No NMI/BRK hijack.
- BCD `ADC`/`SBC` produce correct N/V/Z, at the cost of one extra cycle.
- Undocumented NMOS opcodes become NOPs with a per-opcode timing table.
- Read-modify-write does a dummy **read** where NMOS does a dummy write.

**Additive sub-variant deltas:**

| Variant | Adds |
| --- | --- |
| `Synertek65C02` | Base CMOS set only |
| `Rockwell65C02` | `RMB`/`SMB`/`BBR`/`BBS` |
| `Wdc65C02` | Rockwell's set plus `WAI` and `STP` |

### Task 3: Widen the descriptor model for CMOS

**Files:**
- Modify: `src/SixtyFiveXX/AddrMode.cs`, `src/SixtyFiveXX/Op.cs`, `src/SixtyFiveXX/MicroOp.cs`, `src/SixtyFiveXX/MicroOpTable.cs`, `src/SixtyFiveXX/Cpu.Exec.cs`
- Test: `tests/SixtyFiveXX.Tests/MicroOpTableTests.cs`

No opcode table yet — this adds the vocabulary the table will be written in, so Task 4 is data entry against a model that already works.

- [ ] **Step 1: New addressing modes**

`(zp)` zero-page indirect, `(abs,X)` absolute indexed indirect, and the zero-page-relative mode `BBR`/`BBS` need (a 5-cycle, two-operand form — it is unlike anything in the NMOS set, so do not try to force it into an existing mode).

CMOS also *fixes* `JMP ($xxFF)`. The existing `AddrMode.Indirect` documents itself as reproducing the NMOS bug; CMOS needs the corrected form. Decide deliberately between a second mode and a variant-selected emission, and record which and why — but note the correct 65C02 `JMP (abs)` is also **one cycle longer**, so this is not purely an address-wrap change.

- [ ] **Step 2: New operations**

`Stz`, `Trb`, `Tsb`, `Bra`, `Phx`, `Phy`, `Plx`, `Ply`, `IncA`, `DecA`. Accumulator `INC`/`DEC` are separate members for the same reason `AslA` is separate from `Asl` — they take no effective address.

- [ ] **Step 3: Emission and application**

Extend `Emit`/`EmitAddressing`/`EmitAccess`/`EmitStack` for the new modes, and `Cpu.Exec.cs` for the new operations. `TRB`/`TSB` are read-modify-write.

- [ ] **Step 4: Unit tests for each new mode and operation**

Cycle-exact, written against the documented 65C02 behaviour. These are the fast feedback loop for Task 4 — Harte will be the real gate, but a 2,560,000-vector run is not a debugging tool.

- [ ] **Step 5: The gate — the 6502 is still untouched**

Adding enum members and emission paths must not alter any existing sequence. Full suite, both TFMs.

## Risks

- **Two hand-maintained 256-entry tables that must agree.** The 6502 and CMOS tables share most rows. Build the sub-variant tables *additively* from the CMOS base; three independent copies would be three places for a typo to hide behind a green 6502 suite.
- **`D` cleared on interrupt contradicts a passing test.** Both behaviours must be true at once, per variant. Task 1 lands this before any CMOS opcode exists precisely so the change is attributable.
- **NOP timings are per-opcode, not uniform.** The single most likely source of a broad Harte failure in Task 4.
- **`WAI`/`STP` have no external oracle.** Klaus skips them. The unit tests written in Task 6 are the entire gate.
- **~4–5 GB of vectors.** Task 7 is not optional polish; without it CI downloads gigabytes per run.
- **The exact-set surface test will fail four times** across this phase, once per new public variant. Each is expected and must be fixed by adding the intended type, never by loosening the assertion.
