# Phase 5 — The 6510 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A fifth certified core: the MOS 6510, a 6502 plus the on-chip `$00` data-direction and `$01` I/O port registers — intercepted by the CPU before any bus access.

**Architecture:** The 6510 shares the 6502's opcode table and micro-op sequences unchanged. The only delta is that two addresses stop reaching the bus. That makes this the first variant whose difference is *not* expressible in the opcode table, so the mechanism is new even though the instruction set is not.

**Spec:** `docs/superpowers/specs/2026-08-02-variant-cores-design.md` §"Phase 5"

## Global Constraints

- **The 6502 must not change.** Every existing suite stays green: 10,220,000 vectors across four cores, Klaus functional, Klaus interrupt, Klaus 65C02 extended, and the unit suite — on **both** `net8.0` and `net10.0`.
- **No cost to variants without the port.** The port check sits on the per-cycle path. It must fold away at JIT time for every other variant, and the performance gate must confirm it. If it cannot be made free, report rather than absorb the cost.
- `src/SixtyFiveXX` keeps **zero** NuGet dependencies. `TreatWarningsAsErrors` is on; every public member needs an XML doc comment.
- Conventional Commits. Work on a branch off `main`. **Do not push `main` without `[skip ci]`** — a push cuts a public nuget.org release.

## Established facts — verified this session, do not re-derive

**Two of these correct the spec. Read them before planning around it.**

- **VICE's `testprogs/` are NOT in the GitHub mirror.** `VICE-Team/svn-mirror` contains only `vice/` — 4,099 tree entries, `testprogs` absent entirely, tree not truncated. The tests live in SourceForge SVN, reachable over plain HTTPS:
  `https://svn.code.sf.net/p/vice-emu/code/testprogs/CPU/cpuport/test1.prg`
  Confirmed 200, **138 bytes**: a 2-byte load address of `$0801` then 136 bytes of payload, with a BASIC stub for `SYS 2061` (`$080D`). `KlausCache` cannot be reused unchanged; it hardcodes a raw.githubusercontent base URL and asserts a 64 KB image.
- **`test1` REQUIRES the floating-pin charge model.** The spec says the analog behaviours are "a deliberate non-goal" and implies `test1` certifies only the plain DDR/port semantics. That is wrong. Four of `test1`'s six assertions test the *capacitor* model directly — read `readme.txt` and `test1.s`, both fetched. In order, the test asserts:
  1. `DDR=$FF`, `DATA=$FF` → bit 7 reads 1. *(plain output readback)*
  2. `DDR=$00` → bit 7 **still** reads 1. *(charge retained when the pin goes floating)*
  3. write `$00` to `DATA` while input → bit 7 **still** reads 1. *(a write to an input bit does not change what is read)*
  4. `DDR=$FF`, `DATA=$00` → bit 7 reads 0. *(plain output readback)*
  5. `DDR=$00` → bit 7 **still** reads 0.
  6. write `$FF` to `DATA` while input → bit 7 **still** reads 0.
  What *is* out of scope is the **fade timing**, and `test1` deliberately avoids it — its own comment says "within reasonable time, ie before it faded away". So the charge retention is deterministic and mandatory; only the decay to zero is guesswork, and that is what `bitfade` and `delaytime` measure.
- **`test1` needs no C64.** It writes `$D020`, `$0400` and `$D7FF` as ordinary memory — no VIC-II, CIA or KERNAL is consulted. It ends in a branch-to-self, the same trap shape the Klaus harnesses already handle. **Success:** `$D7FF == $00`. **Failure:** `$D7FF == $FF`, plus a digit at `$0400` identifying which of the six steps failed.
- **`initvalue` is out of scope and cannot be used.** It asserts `DATA` reads `$17` from a reset DDR — that value comes from *pull-up resistors on the C64 board*, not from the CPU. It also ships as a `.crt`.
- The 6510 reuses `Opcodes6502.Table` unchanged, and `MicroOpTable.SequencesFor` already returns the NMOS profile for `CpuVariant.Mos6510` explicitly.
- `CpuVariant.Mos6510` already exists. `PublicSurfaceTests` asserts an **exact** public type set, so adding `Mos6510Variant` **will fail it by design** — fix by adding the intended type, never by loosening the assertion.

### Task 1: The variant, with no port yet

**Files:** Create `Variants/Mos6510Variant.cs`; modify `MicroOpTable.cs`, `PublicSurfaceTests.cs`, `HarteTests.cs`

The 6510's inherited behaviour is the 6502's. Landing the variant alone proves that before any port logic exists.

- [ ] **Step 1: Wire it up.** `Mos6510Variant` reporting `CpuVariant.Mos6510`; `OpcodeTableFor` returns `Opcodes6502.Table`.
- [ ] **Step 2: Run the 6502's own gates against it.** There is no `mos6510` vector set anywhere, so the 6510 is certified on inherited opcodes by running the **6502's** Harte set against the 6510 core. Add that as its own conformance class — 2,560,000 vectors — and the Klaus functional and interrupt programs likewise.
- [ ] **Step 3: Surface test, then commit.**

---

### Task 2: The port registers

**Files:** Create `CpuPort.cs`; modify `Cpu.cs`

- [ ] **Step 1: Decide how the check folds away, and measure it**

Every bus access must consult two addresses only for this one variant. `TVariant.Variant` is a compile-time constant per closed generic type, so `if (TVariant.Variant == CpuVariant.Mos6510)` should fold to nothing for every other core — but *should* is not *does*. Confirm with the performance gate before and after, on a quiet machine, and report both figures. Adding a member to `ICpuVariant` is the alternative; it is a public API change, so prefer the fold if it measures free.

- [ ] **Step 2: The register semantics**

`$00` is the direction register, `$01` the port. A bit set in `$00` is an output. Reading `$01` returns output bits as last written. Writes to `$00`/`$01` never reach the bus, and neither do reads.

- [ ] **Step 3: Unit tests, then commit.** Include that the underlying RAM at `$0000`/`$0001` is untouched by a port write — the registers intercept, they do not shadow.

---

### Task 3: The floating bits

**Files:** Modify `CpuPort.cs`; test in `tests/SixtyFiveXX.Tests/`

Bits 6 and 7 have no external connection on the 6510. This is the part the spec wrongly calls out of scope — see the established facts. **Model the charge, not the fade.**

- [ ] **Step 1: The model.** An unconnected bit programmed as output stores the value written. Switched to input, reads return that stored value. A write while in input mode does not change what is read. No timer, no decay — a bit holds its charge indefinitely here, and that divergence from hardware is deliberate and must be documented where a reader will find it.
- [ ] **Step 2: Tests mirroring `test1`'s six steps**, written from the fetched source, so a failure points at the same step number the VICE program reports.
- [ ] **Step 3: Commit.**

### Task 4: The VICE `cpuport` gate

**Files:** Create `ViceCache.cs`, `VicePortTests.cs`

- [ ] **Step 1: Fetch and cache.** SourceForge over HTTPS, cached like the Klaus binaries, with `SIXTYFIVEXX_VICE_DIR` for offline runs. A `.prg` is a 2-byte load address followed by data — load it at that address rather than assuming a 64 KB image.
- [ ] **Step 2: Run it.** Entry `$080D`; run to a branch-to-self. Assert `$D7FF == $00`. On failure report the digit at `$0400`, which names the failing step.
- [ ] **Step 3: Prove the gate discriminates.** Break one port behaviour deliberately and confirm the program reports failure rather than passing. **This is the only independent oracle the 6510 has** — a gate that cannot fail is worse than no gate, because it looks like certification.
- [ ] **Step 4: Commit.**

## Risks

- **One external oracle, and it is smaller than it looks.** `test1` is 136 bytes and checks bit 7 only. It says nothing about bits 0-5, nothing about `$00`'s own readback, and nothing about the interaction with the bus. The unit tests are not a supplement here; for most of the port they are the whole gate — the same position `WAI`/`STP` were in during phase 4.
- **The spec is wrong about scope**, and following it would produce a core that fails the only gate available. See the established facts.
- **The port check is on the per-cycle path.** If it does not fold away, every other core pays for a feature it does not have.
- **No 6510 vector set exists**, so "certified" here means the 6502's vectors run against the 6510 core plus a 136-byte program. That is a weaker claim than phase 4's and should be stated as such rather than blurred into the same word.
