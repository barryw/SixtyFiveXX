# Research: What sim6502 needs from a CPU core

Read-only research. No code changed in either repository. All line numbers verified by
reading the file at that offset on 2026-08-02; quotes are exact.

## 1. What emulator does sim6502 use today?

**A hand-written, vendored 6502 core — not a package.** `sim6502/sim6502.csproj` has no
`PackageReference` to any CPU/emulator package:

```xml
<PackageReference Include="Antlr4.Runtime.Standard" Version="4.13.1" />
<PackageReference Include="CommandLineParser" Version="2.9.1" />
<PackageReference Include="NLog" Version="5.3.4" />
```

The core lives at `sim6502/Proc/` as a `partial class Processor` (3,862 lines across 11
files: `Processor.Core.cs`, `Processor.Execution.cs`, `Processor.Memory.cs`,
`Processor.Addressing.cs`, `Processor.Operations.cs`, `Processor.Disassembly.cs`,
`OpcodeRegistry.cs`, `OpcodeHandler.cs`, `AddressingMode.cs`, `Disassembly.cs`,
`ProcessorType.cs`). Every one of those files carries the same header:

```
Copyright (c) 2013, Aaron Mell
All rights reserved.
...
Logger.Info("https://github.com/aaronmell/6502Net");
```

This is a fork/derivative of Aaron Mell's `6502Net` (BSD-3-Clause), heavily modified in
place over years of commits (`git log --oneline -- sim6502/Proc` shows 20+ refactor/feat
commits: extracting partials, adding an opcode registry, adding `ProcessorType`, adding
65C02 opcodes). It is source, not a binary dependency, and is `sim6502`'s own code as far
as versioning/build is concerned — there is no version number, no changelog, no upstream
sync mechanism.

The `dependencies/` folder at the repo root contains only `antlr-4.13.1-complete.jar`
(the ANTLR grammar generator tool), unrelated to the CPU.

## 2. What is the exact surface sim6502 consumes?

The important discovery: **sim6502 does not talk to `Processor` directly as its primary
seam.** It talks to `IExecutionBackend` (`sim6502/Backend/IExecutionBackend.cs`), and
`SimulatorBackend` (`sim6502/Backend/SimulatorBackend.cs`) is the adapter that owns a
`Processor` and translates backend calls into `Processor` calls. `Processor` itself is
consumed in exactly three places outside `sim6502/Proc/`:

- `sim6502/Backend/SimulatorBackend.cs` — the adapter (full detail below)
- `sim6502/Backend/U64SimBackend.cs:49` — `CycleCounter = () => _sim.Processor.CycleCount` (reads one property through an internal `SimulatorBackend`)
- `sim6502/Grammar/SimBaseListener.cs:193` — `public Processor? Proc => (Backend as SimulatorBackend)?.Processor;`, a debug escape hatch used **only by tests** (`sim6502tests/TestSuiteParser.cs`) to assert directly against `Processor` state instead of through `IExecutionBackend`.

So there are two surfaces to satisfy: the `IExecutionBackend` contract (used by all
production code paths), and the raw `Processor` surface reachable via `.Proc` (used only
by `TestSuiteParser.cs`, which could in principle be rewritten to go through
`IExecutionBackend` instead).

### 2a. `IExecutionBackend` — the real seam (`sim6502/Backend/IExecutionBackend.cs`)

```csharp
public interface IExecutionBackend : IDisposable
{
    // Memory operations
    void LoadBinary(byte[] data, int address);
    void WriteByte(int address, byte value);
    void WriteWord(int address, int value);
    void WriteMemoryValue(int address, int value);
    byte ReadByte(int address);
    int ReadWord(int address);

    // Register operations
    int GetRegister(string name);
    void SetRegister(string name, int value);

    // Flag operations
    bool GetFlag(string name);
    void SetFlag(string name, bool value);

    // Execution
    ExecutionResult ExecuteJsr(int address, int stopOnAddress, bool stopOnRts, bool failOnBrk);
    int GetCycles();
    void ResetCycleCount();

    // Symbols
    void LoadSymbols(string path);

    // State management
    void SaveSnapshot(string name);
    void RestoreSnapshot(string name);
    void Reset();

    // Configuration
    void SetWarpMode(bool enabled);

    // Trace support
    bool TraceEnabled { get; set; }
    void ClearTraceBuffer();
    List<string> GetTraceBuffer();
}
```

21 members. `SimulatorBackend` implements each by delegating to `Processor`
(`sim6502/Backend/SimulatorBackend.cs`):

| IExecutionBackend member | Processor member it calls | Group |
|---|---|---|
| `LoadBinary` | `Processor.LoadProgram(address, data, address, false)` | memory |
| `WriteByte` | `Processor.WriteMemoryValueWithoutIncrement(address, value)` | memory |
| `WriteWord` | `Processor.WriteMemoryWord(address, value)` | memory |
| `WriteMemoryValue` | `Processor.WriteMemoryValue(address, value)` | memory |
| `ReadByte` | `Processor.ReadMemoryValueWithoutCycle(address)` | memory |
| `ReadWord` | `Processor.ReadMemoryWordWithoutCycle(address)` | memory |
| `GetRegister("a"/"x"/"y")` | `Processor.Accumulator` / `.XRegister` / `.YRegister` (get) | registers |
| `SetRegister(...)` | same three (set) | registers |
| `GetFlag("c"/"z"/"n"/"v"/"d")` | `.CarryFlag` / `.ZeroFlag` / `.NegativeFlag` / `.OverflowFlag` / `.DecimalFlag` (get) | flags |
| `SetFlag(...)` | same five (set) | flags |
| `ExecuteJsr` | `Processor.RunRoutine(address, stopOnAddress, stopOnRts, failOnBrk)`, then reads `.CycleCount`, `.ProgramCounter` | execution control |
| `GetCycles` | `Processor.CycleCount` (get) | execution control |
| `ResetCycleCount` | `Processor.ResetCycleCount()` | execution control |
| `LoadSymbols` | no-op (`{ }`) — not implemented for `sim` backend | symbols |
| `SaveSnapshot`/`RestoreSnapshot` | no-op — not implemented for `sim` backend | state mgmt |
| `Reset` | `Processor.Reset()` | execution control |
| `SetWarpMode` | no-op — VICE-only concept | config |
| `TraceEnabled` get/set | `Processor.TraceEnabled` get/set | trace |
| `ClearTraceBuffer` | `Processor.ClearTraceBuffer()` | trace |
| `GetTraceBuffer` | `Processor.GetTraceBuffer()` | trace |

So the **actual** `Processor` surface load-bearing for the `sim` backend is:

- **Construction**: `Processor(ProcessorType, IMemoryMap)` constructor (`SimulatorBackend.cs:15`)
- **Execution control**: `Reset()`, `RunRoutine(int, int, bool, bool)`, `CycleCount` (get),
  `ResetCycleCount()`, `ProgramCounter` (get)
- **Memory access**: `LoadProgram(int, byte[], int, bool)`,
  `WriteMemoryValueWithoutIncrement(int, byte)`, `WriteMemoryWord(int, int)`,
  `WriteMemoryValue(int, int)`, `ReadMemoryValueWithoutCycle(int)`,
  `ReadMemoryWordWithoutCycle(int)`
- **Register access**: `Accumulator`, `XRegister`, `YRegister` (get/set, `int`-typed)
- **Flag access**: `CarryFlag`, `ZeroFlag`, `NegativeFlag`, `OverflowFlag`, `DecimalFlag`
  (get/set, `bool`)
- **Debugging/tracing**: `TraceEnabled` (get/set), `ClearTraceBuffer()`, `GetTraceBuffer()`
  — confirmed live (not dead code): `SimBaseListener.cs` wires a DSL `trace = true` test
  option through exactly these three members (`SimBaseListener.cs:1071-1074`,
  `:223-224`, `:305`) to dump per-instruction disassembly on a failing test.

Notably **absent** from what `IExecutionBackend`/`SimulatorBackend` touch:
`DisableInterruptFlag`, `TriggerNmi`, `TriggerIrq`, `InterruptRequest()`,
`StackPointer`, `CurrentOpCode`, `CurrentDisassembly`, `ConvertOpCodeIntoString`,
`IsBrk`/`IsRts`/`IsJsr`, `NextStep()`, `DumpMemory()`, `ClearMemory()`,
`CycleCountIncrementedAction`. These exist on `Processor` and are used *inside*
`sim6502/Proc/` (e.g. `RunRoutine` calls `NextStep()` internally, which itself checks
`IsJsr`/`IsRts`/`IsBrk` and processes `TriggerNmi`/`TriggerIrq`) but are not reached from
outside the `Proc` namespace except via the `.Proc` test escape hatch below. **sim6502's
production code path never asserts an IRQ or NMI against the `sim` backend** — no caller
of `IExecutionBackend` invokes anything interrupt-related. (`ProcessorFlag()` matches at
`SimBaseListener.cs:795,861` are DSL grammar tokens for the `GetFlag`/`SetFlag` calls
above, not interrupt lines.)

### 2b. The `.Proc` test-only surface (`sim6502tests/TestSuiteParser.cs`)


All members already covered above — no new surface. This is redundant with what
`IExecutionBackend` exposes and looks like it could be rewritten against the interface,
but as written it is a second, parallel consumer of `Processor`'s public surface, and
`sim6502tests/Backend/SimulatorBackendTests.cs:109-110` also touches
`backend.Processor` / `.ProcessorType` directly (`SimulatorBackend.Processor` is a public
property).

### 2c. Everything else in `sim6502.Proc` (`AddressingMode`, `OpcodeHandler`,
`OpcodeRegistry`, `Disassembly`, `LoadableResource`) is internal machinery not referenced
outside `sim6502/Proc/` at all — confirmed by grepping every `.cs` file in the solution
for `sim6502.Proc` usages; only the files listed above import it.

### Tally

Distinct `Processor` members actually reached from outside `sim6502/Proc/`: **2
constructors + ~24 methods/properties** (6 memory methods, 3 register properties ×2
accessors, 5 flag properties ×2 accessors, `Reset`, `RunRoutine`, `CycleCount`,
`ResetCycleCount`, `ProgramCounter`, `TraceEnabled`×2, `ClearTraceBuffer`,
`GetTraceBuffer`, plus `ProcessorType` read in tests) ≈ **28 distinct members**. That is
the compatibility target for the `sim` backend specifically. (The other five backends —
`vice`, `novavm`, `verilator`, `u64sim`, `u64` — never touch `Processor` at all; see §4.)

## 3. Which 65xx variants does sim6502 support or intend to?

Real, present, partial support for three variants via `ProcessorType`
(`sim6502/Proc/ProcessorType.cs`):

```csharp
public enum ProcessorType
{
    MOS6502 = 0,
    MOS6510 = 1,   // 6502 with I/O port at $00-$01 (C64)
    WDC65C02 = 2,  // CMOS variant with additional opcodes
}
```

- **6502**: baseline, documented opcodes only. `OpcodeRegistry`'s comment history says
  "all 151 opcodes" — this is the 151 *documented* NMOS opcodes. **No undocumented/illegal
  opcode support** — confirmed by `ExecuteOpCode()` throwing `NotSupportedException` for
  any opcode not in the registry (`Processor.Execution.cs:234-238`).
- **6510**: shares the 6502 opcode table (`_processorOpcodes[ProcessorType.MOS6510] =
  _processorOpcodes[ProcessorType.MOS6502]`, `OpcodeRegistry.cs:52`) plus hand-rolled I/O
  port emulation for addresses `$00`/`$01` built directly into `ReadMemoryValue` /
  `WriteMemoryValue` / `WriteMemoryValueWithoutIncrement`
  (`sim6502/Proc/Processor.Memory.cs:67-80,98-110,150-165,183-198`) — but **only when
  `MemoryMap` is null**; when a memory map is supplied (the normal path via
  `SimulatorBackend`), the I/O port instead has to be handled by the memory map
  implementation (see `sim6502/Systems/Generic6510MemoryMap.cs`, not read in this pass).
- **65C02**: has its own, separately-populated opcode dictionary
  (`_processorOpcodes[ProcessorType.WDC65C02] = new Dictionary<...>()`) that is
  demonstrably incomplete but growing — commit history shows `STZ`, `PHX/PLX/PHY/PLY`,
  and `BRA` added incrementally, and `Processor.Disassembly.cs`'s
  `ConvertOpCodeIntoString` recognizes 65C02 opcodes (`STZ`, `TRB`, `TSB`, `BRA`, the
  `(zp)` indirect forms of `ADC`/`AND`/`CMP`/`EOR`/`LDA`/`ORA`/`SBC`/`STA` at `$72/$32/
  $D2/$52/$B2/$12/$F2/$92`). There is a 14th `AddressingMode.ZeroPageIndirect` added
  specifically for 65C02 `(zp)` addressing (`AddressingMode.cs:119-123`).
- **65816**: **no trace of it anywhere** — no enum member, no opcode table, no 16-bit
  register handling, no bank-byte addressing.
- **Decimal mode**: `DecimalFlag` property exists and is read/written through
  `IExecutionBackend.GetFlag("d")`/`SetFlag("d")`; ADC/SBC decimal-mode arithmetic itself
  lives in `Processor.Operations.cs` (not fully re-read this pass, but the flag plumbing
  and opcode dispatch confirm it's implemented for the NMOS variant, consistent with the
  151-opcode registry).
- The DSL surfaces variant selection directly: `SimBaseListener.cs:45-54` maps
  `processorTypeValue` grammar productions (`ProcessorType6502()`, `ProcessorType6510()`,
  `ProcessorType65C02()`) to `ProcessorType`, so `.suite` test files can declare which
  chip they're testing.

**Verdict**: sim6502 is not 6502-only. It actively supports 6502, 6510 (C64 I/O port),
and a work-in-progress subset of 65C02, with the DSL already parameterized on the
variant. It has no 65816 ambition visible in this repo today, but the shape (a
`ProcessorType`/system-type indirection reaching into `MemoryMapFactory`) is exactly the
kind of thing that would need a matching `CpuVariant` (see §6) on the SixtyFiveXX side.

## 4. What does sim6502 do that a bare CPU core cannot?

sim6502 is fundamentally a **BASIC-like DSL test framework with six pluggable execution
backends**, of which the CPU core discussed above powers exactly one (`sim`). From
`README.md`:

> sim6502 now has six execution backends: `sim` (fast internal 6502/6510/65C02
> assembly-unit tests), `vice` (hardware-accurate C64 tests through a VICE MCP server),
> `novavm` (BASIC-level integration tests against the e6502/NovaVM Avalonia emulator),
> `verilator` (against an FPGA Verilator simulation), `u64sim` (Ultimate 64 feature tests
> against a simulated UCI), `u64` (differential check against a real Ultimate 64 over
> REST).

Scale by directory (`.cs` line counts, excluding `obj`/`bin`):

| Directory | Lines | Purpose |
|---|---|---|
| `sim6502/Proc` | 3,862 | the CPU core itself |
| `sim6502/Backend` | 2,205 | `IExecutionBackend` + 5 non-`sim` backends (VICE, NovaVM, Verilator, U64 sim, real U64 hardware — RCP/socket/REST clients) |
| `sim6502/Systems` | 2,147 | memory maps (`C64MemoryMap`, `Generic6510MemoryMap`, `GenericMemoryMap`), I/O handler registration, Ultimate 64 UCI register model |
| `sim6502/Grammar` | 13,602 (incl. ANTLR-generated parser) | the test DSL: parser, listener (`SimBaseListener.cs` alone drives all test execution/assertion logic), lexer |
| `sim6502/Expressions` | 137 | expression evaluation for assertions (`assert([addr] == value)`) |
| `sim6502/Errors` | 439 | DSL error reporting |
| `sim6502/Utilities` | 272 | file loading helpers |
| `sim6502-lsp` | separate project | Language Server Protocol implementation for the DSL (editor tooling) — does **not** reference `sim6502.Proc` at all |
| `sim6502-vscode` | separate project (TypeScript) | VS Code extension for the DSL |

Responsibilities that are sim6502's, not the CPU's, and would stay put under any CPU
swap:
- **The test DSL** (parsing, suite/test/assert grammar, symbol tables from `.sym` files,
  expression evaluation) — 13.6k+ lines, entirely orthogonal to the CPU.
- **Memory mapping / banking** (`IMemoryMap`, `C64MemoryMap`, ROM overlays, I/O handler
  registration) — already abstracted away from `Processor` (see §5).
- **Backend abstraction and 5 of 6 backends** (VICE, NovaVM, Verilator, U64-sim, real
  Ultimate 64) — these don't use `sim6502.Proc` at all; they talk to external processes/
  hardware over sockets/REST. A CPU-core swap is scoped to the `sim` backend only.
- **Symbol table loading**, used for readable assertions against labeled addresses —
  DSL-level, backend-agnostic (`IExecutionBackend.LoadSymbols`, no-op on `sim` today
  anyway).
- **Editor tooling** (LSP + VS Code extension) — entirely independent of the CPU.
- **The Ultimate 64 UCI register model** (`sim6502/Systems/Ultimate/`) — hardware
  register semantics for a specific piece of real hardware, unrelated to any CPU core.

## 5. How is the current core wired in?

There **is** an existing abstraction, but it sits one level up: `IExecutionBackend`
wraps whichever engine executes code, and `SimulatorBackend` is a thin concrete adapter
between `IExecutionBackend` and the concrete `Processor` class. `Processor` itself has no
interface — it is a concrete `partial class`, directly `new`'d:

```csharp
// sim6502/Backend/SimulatorBackend.cs
public class SimulatorBackend : IExecutionBackend
{
    public Processor Processor { get; }

    public SimulatorBackend(ProcessorType processorType, IMemoryMap memoryMap)
    {
        Processor = new Processor(processorType, memoryMap);
        Processor.Reset();
    }
    ...
}
```

Selection happens in `sim6502/Backend/BackendFactory.cs`:

```csharp
case "sim":
    return new SimulatorBackend(processorType, memoryMap);
```

So the seam a replacement core would implement is **not** "become a drop-in
`Processor`" — it is "back a new/updated `SimulatorBackend` that still satisfies
`IExecutionBackend`." That is a much smaller, cleaner target (21 interface members, all
listed in §2a) than porting `Processor`'s full public surface. The one wrinkle is
`SimulatorBackend.Processor` being a public property (`SimulatorBackend.cs:11`) reached
by `U64SimBackend.cs:49` and two test files (§2b) — those three call sites would need to
either go through `IExecutionBackend` instead, or the replacement's equivalent exposed
type would need to support `.CycleCount`, `.XRegister`/`.Accumulator`/`.YRegister`,
`.CarryFlag`/`.ZeroFlag`/`.NegativeFlag`/`.OverflowFlag`/`.DecimalFlag`,
`.ReadMemoryValueWithoutCycle`/`.ReadMemoryWordWithoutCycle`, and `.ProcessorType`.

There is also a memory-side seam already in place: `IMemoryMap`
(`sim6502/Systems/IMemoryMap.cs`) — `Read`, `Write`, `ReadWithoutCycle`,
`WriteWithoutCycle`, `LoadRom`, `LoadProgram`, `GetRam`, `Reset`,
`IncrementCycleCount` (an `Action` property the processor assigns itself into, so the map
can report cycle-accurate timing back), and an optional `RegisterIoHandler` with a
default-interface no-op. `Processor`'s memory methods check `MemoryMap != null` and
delegate every operation to it when present (`Processor.Memory.cs`); this is a genuinely
clean, already-abstracted seam that a replacement core's bus adapter would need to speak
to, independent of whatever `IBus` shape SixtyFiveXX offers.

## 6. What would break? — gap list against SixtyFiveXX (`src/SixtyFiveXX/`)

Read: `Cpu.cs` (738 lines), `Cpu.Exec.cs` (331), `CpuState.cs` (97), `CpuVariant.cs` (23),
`IBus.cs` (76), `Opcodes6502.cs` (301, `internal`), `MicroOp.cs`/`MicroOpTable.cs`,
`OpcodeInfo.cs` (16, `internal`), `Op.cs` (65, `internal`). Also `README.md`'s status
table:

| Variant | State | Certified against |
|---|---|---|
| 6502, documented opcodes | Complete | Harte SingleStepTests, per-cycle |
| 6502, undocumented opcodes | Complete | Harte SingleStepTests, per-cycle |
| 65C02 (Rockwell, Synertek, WDC) | Phase 4 | — |
| 6510 | Phase 5 | — |
| 65816 | Phase 7 | — |

### Maps cleanly

- **Registers**: `CpuState` (`public ushort PC; byte A,X,Y,S,P;` plus bool flag
  properties `C/Z/I/D/V/N` over `P`) is a strict superset, in a nicer shape, of what
  `IExecutionBackend.GetRegister/SetRegister("a"|"x"|"y")` and
  `GetFlag/SetFlag("c"|"z"|"n"|"v"|"d")` need. `Cpu<TBus>.State` returns `ref CpuState`,
  so a `SimulatorBackend`-equivalent adapter can do `cpu.State.A` /
  `cpu.State.C = value` directly — a straightforward string-switch shim over `ref
  CpuState`, same shape as today's `SimulatorBackend.GetRegister`/`SetFlag`.
- **Bus/memory model**: `IBus.Read(int)/Write(int, byte)` is a strict subset of what
  `IMemoryMap` needs; `sim6502`'s `IMemoryMap` (`Read`, `Write`, `ReadWithoutCycle`,
  `WriteWithoutCycle`, `GetRam`, `LoadProgram`, `LoadRom`, `Reset`,
  `IncrementCycleCount`, `RegisterIoHandler`) would become the concrete `struct IBus`
  implementation (or be wrapped via `RefBus` for the runtime-polymorphic case — see
  below), not something SixtyFiveXX needs to grow.
- **Execution control**: `Cpu<TBus>.Step()` (runs to the next instruction boundary,
  returns cycles consumed) is a fair analog of `Processor.NextStep()` +
  cycle-accounting; `Run(long cycles)` and `RunUntil(Func<Cpu<TBus>,bool>, long
  maxCycles)` together cover what `RunRoutine`/`ExecuteJsr` do (stop-on-address,
  cycle-budget), though the *exact* stop conditions (`stopOnRts`, `failOnBrk`,
  subroutine-depth counting via JSR/RTS balance) are not built in and would need to be
  reimplemented as a `stop` predicate using `AtInstructionBoundary` plus bus-side
  tracking of JSR/RTS — `Cpu<TBus>` doesn't expose "was the last opcode a JSR/RTS/BRK,"
  so that predicate would have to snoop the bus reads itself.
- **Cycle counting**: `Cpu<TBus>.Cycles` / `ResetCycleCount()` map directly onto
  `Processor.CycleCount` / `.ResetCycleCount()`.
- **Interrupts**: `SetIrq(bool)` / `SetNmi(bool)` / `Ready` / `SetRdy(bool)` / `SetSo()`
  are present and, per the extensive doc comments in `Cpu.cs`, considerably more
  cycle-accurate than sim6502's own `ProcessNmi`/`ProcessIrq`
  (`sim6502/Proc/Processor.Operations.cs:546-568`, a same-cycle push/vector jump with no
  documented handling of CLI/SEI-delayed recognition or BRK/NMI hijacking). sim6502's
  production `IExecutionBackend` path never exercises interrupts today (§2a), so this is
  a net improvement, not a regression, but it means **sim6502 would gain interrupt
  fidelity it doesn't currently test for** if it ever wired IRQ/NMI through the DSL.
- **6502 opcode completeness**: SixtyFiveXX implements and Harte-certifies all 256
  opcodes including the 105 undocumented ones; sim6502's own registry implements only
  the 151 documented ones and throws `NotSupportedException` on anything else
  (`Processor.Execution.cs:234-238`). Another net improvement, not a gap.

### What SixtyFiveXX lacks that sim6502 depends on

1. **No disassembler / no trace buffer.** sim6502's DSL has a live, user-facing
   `trace = true` test option (`SimBaseListener.cs:1071-1074`) that dumps
   per-instruction disassembly on failure, driven by `Processor.TraceEnabled`,
   `.GetTraceBuffer()`, `.ClearTraceBuffer()`, and internally `SetDisassembly()` /
   `ConvertOpCodeIntoString(int)` (`Processor.Disassembly.cs`, 578 lines, a full
   opcode→mnemonic table plus operand formatting per addressing mode). SixtyFiveXX has
   no equivalent anywhere — `OpcodeInfo.Mnemonic` exists but `OpcodeInfo` and `Op` are
   both `internal`, unreachable from a host assembly. This is the single largest
   feature gap for `sim6502` specifically, since it's an advertised, working debugging
   feature.
2. **No variant switch wired to execution.** `CpuVariant` (`Mos6502`, `Mos6510`,
   `Wdc65C02`, `Rockwell65C02`, `Synertek65C02`, `W65C816`) exists as an enum, but
   `Cpu<TBus>`'s constructor hardcodes `_table = MicroOpTable.Mos6502;`
   (`Cpu.cs:101-107`) with no way to select a different micro-op table or opcode table
   at construction time. sim6502 needs `ProcessorType.MOS6510`/`.WDC65C02` to actually
   change behavior (I/O port at `$00`/`$01` for 6510 — no equivalent hook in
   SixtyFiveXX at all; a different opcode table for 65C02 — table exists in principle
   via `CpuVariant` but isn't loadable). Per the README, 65C02/6510/65816 are Phase
   4/5/7 — not yet implemented, just reserved enum slots.
3. **No convenience memory/load API.** `Processor.LoadProgram(offset, byte[], pc,
   reset)` (used by `SimulatorBackend.LoadBinary`), `WriteMemoryWord`,
   `ReadMemoryWordWithoutCycle`, and the byte-vs-word-overloaded `WriteMemoryValue(int,
   int)` don't exist on `IBus`/`Cpu<TBus>` — `IBus` is single-byte read/write only. A
   `sim6502`-facing adapter would need to implement word-read/write and program-loading
   itself against the bus, which is a small but real amount of new code (not present
   today in either repo).
4. **No register-by-name / flag-by-name accessor**, no snapshot save/restore hook, no
   symbol-loading hook — none of these are CPU-core concerns and none exist on
   `Cpu<TBus>`; they'd be built into the new `SimulatorBackend`-equivalent adapter, same
   as today (`LoadSymbols`/`SaveSnapshot`/`RestoreSnapshot`/`SetWarpMode` are already
   no-ops in `SimulatorBackend` for the `sim` backend, so this is low-risk — nothing
   currently depends on them working).
5. **No `IsBrk`/`IsRts`/`IsJsr` or subroutine-depth tracking**, needed to reproduce
   `RunRoutine`'s `stopOnRts`/`failOnBrk` semantics exactly (see "Execution control"
   above) — would have to be rebuilt by watching bus reads at instruction boundaries,
   external to `Cpu<TBus>`.

### Where the shapes differ enough to need an adapter

- **`Cpu<TBus> where TBus : struct, IBus`** — the generic-struct-bus design the task
  flagged is real and exactly as unusual as described. sim6502 currently resolves its
  memory map at runtime from DSL content (`MemoryMapFactory.CreateForSystem`/
  `CreateForProcessor`, chosen per `.suite` file, not per compile), and
  `SimulatorBackend`'s constructor takes an `IMemoryMap` **reference**, decided at
  runtime. `Cpu<TBus>` cannot do that directly — `TBus` is fixed at the generic
  instantiation, i.e. compile time (or at minimum, one concrete closed generic type
  per call site). SixtyFiveXX already ships the fix for this exact scenario: `RefBus`
  (`IBus.cs:60-76`), a `readonly struct RefBus : IBus` that wraps any `IBus` **reference**
  chosen at runtime, at the cost of one virtual dispatch per access (explicitly
  documented: "Costs one interface dispatch per access, so the JIT cannot inline memory
  accesses. Use it when the bus must be chosen at runtime"). A sim6502 adapter would
  almost certainly instantiate `Cpu<RefBus>` and wrap its existing `IMemoryMap` in an
  `IBus`-shaped facade, trading some throughput for keeping the current
  runtime-polymorphic memory-map architecture unchanged. This is a real architectural
  seam to design, not a trivial renaming — but SixtyFiveXX has already anticipated it.
- **Byte vs. int typing.** `Processor.Accumulator`/`.XRegister`/`.YRegister` are `int`
  (explicitly, per the doc comment, "so we can detect wrapping of the value"); `CpuState.A/X/Y`
  are `byte`. `IExecutionBackend.GetRegister`/`SetRegister` are also `int`-typed. A
  narrowing/widening conversion is needed at the adapter boundary; low risk, since 6502
  registers never legitimately hold anything outside 0-255 in `SixtyFiveXX`'s model
  (values are masked/wrapped inside `Cpu.Exec.cs`, not left to overflow for the caller
  to detect).
- **`ProcessorType` (sim6502) vs. `CpuVariant` (SixtyFiveXX)** — same idea, different
  enum, and SixtyFiveXX's isn't wired to anything yet (gap #2 above). Values don't
  line up 1:1 either: `CpuVariant` distinguishes `Wdc65C02`/`Rockwell65C02`/
  `Synertek65C02`; `ProcessorType` has just one `WDC65C02`. Reconciling which sim6502
  opcode table maps to which `CpuVariant` is a design decision, not a mechanical one.

## 7. Scale and risk

**sim6502 overall**: ~11,440 non-generated `.cs` lines in the main `sim6502` project
(excluding `Grammar/Generated`, which is another 11,607 lines of ANTLR-emitted parser
code), plus `sim6502-lsp` and `sim6502-vscode` as fully separate projects untouched by
any CPU change. Of the hand-written total, the CPU core (`sim6502/Proc/`) is 3,862
lines — roughly a third of the non-generated main project, and a small fraction of the
whole repo once the DSL grammar, LSP, and VS Code extension are counted. **A CPU swap is
narrowly scoped**: it touches `sim6502/Proc/` (deleted or replaced), `SimulatorBackend`
(rewritten), and the three call sites into `SimulatorBackend.Processor` (§2b/§5); it does
not touch the DSL, the other five backends, `Systems/` memory maps (only their `IBus`
adaptation), or either editor-tooling project.

**Test coverage that would catch a bad swap**: `sim6502tests/` is 55 files, 15,916
lines — larger than the CPU core itself. Directly relevant:
- `ProcessorTests.cs`, `ProcessorExecutionTests.cs`, `ProcessorTypeTests.cs`,
  `Processor6510Tests.cs`, `Opcodes65C02Tests.cs`, `OpcodeRegistryTests.cs`,
  `StackPointerWrappingTests.cs` — unit tests directly against `Processor`.
- `KlausDormannFunctionalTests.cs` — runs Klaus Dormann's `6502_functional_test.bin`
  (the same conformance suite SixtyFiveXX's own `tests/SixtyFiveXX.Conformance/`
  already uses — `KlausFunctionalTests.cs`, `KlausInterruptTests.cs`), 100M-cycle ceiling,
  tagged `[Trait("Category", "Slow")]`.
- `Backend/SimulatorBackendTests.cs`, `Backend/BackendFactoryTests.cs`,
  `Backend/U64SimBackendTests.cs` — test the seam itself.
- `TestSuiteParser.cs` — exercises the `.Proc` escape hatch end-to-end through actual
  `.suite` DSL programs.

This is a real regression net, not a thin one: both a hand-unit-test layer and a
whole-program functional-test layer (Klaus Dormann) already exist and overlap almost
exactly with what SixtyFiveXX already certifies against (Klaus + Harte). That overlap is
good news for validating a swap — the same conformance fixture can plausibly gate both
projects — but I did not verify whether sim6502's copy of the Klaus Dormann binary tests
interrupts (SixtyFiveXX's `KlausInterruptTests.cs` name suggests SixtyFiveXX runs an
interrupt-specific Klaus Dormann test that sim6502's single `AllOpcodes_ShouldPassFunctionalTest`
may not cover) — **unconfirmed, would need a byte-for-byte diff of the two `.bin`/`.lst`
fixtures to settle.**

**Risk concentration**: the highest-risk item is not the opcode/flag surface (well
covered by tests on both sides) but the two features with zero test signal on the
SixtyFiveXX side because they don't exist yet: trace/disassembly (§6, gap 1) and 6510
I/O-port/65C02-table variant switching (§6, gap 2). Both are things sim6502's test suite
*would* catch immediately if a naive swap silently dropped them (`TestSuiteParser.cs`
exercises `trace` DSL option paths; `Processor6510Tests.cs`/`Opcodes65C02Tests.cs`
exercise variant behavior) — so the risk is schedule/scope risk (these need to be built),
not silent-breakage risk.

## Honesty about gaps in this research

- I did not read `Processor.Operations.cs` or `Processor.Addressing.cs` in full (1,014
  combined lines) — I sampled the interrupt handlers and 65C02 stack ops. Decimal-mode
  ADC/SBC correctness on the sim6502 side is inferred from flag plumbing and opcode
  registration, not read line-by-line. If exact decimal-mode NMOS quirks matter for the
  migration, both implementations should be read in full and diffed against a fixture.
- I did not read `sim6502/Systems/C64MemoryMap.cs`, `Generic6510MemoryMap.cs`,
  `GenericMemoryMap.cs`, or `IIOHandler.cs` in full — I inferred their role from
  `IMemoryMap`'s interface and `MemoryMapFactory`'s usage. The exact shape of I/O-handler
  registration (used for VIC/SID/CIA register ranges on the C64 map) is not captured
  here in detail; anyone designing the `IBus` adapter should read these directly.
  found in this pass would need the C64 memory map's true behavior, best settled by
  reading `C64MemoryMap.cs` directly.
- I did not diff sim6502's Klaus Dormann fixture (`sim6502tests/FunctionalTests/`)
  against SixtyFiveXX's (`tests/SixtyFiveXX.Conformance/klaus/`) to confirm whether
  they're the same test binary/version or whether sim6502's covers interrupts. Settle by
  comparing file hashes/sizes and reading both `KlausDormannFunctionalTests.cs` (sim6502)
  and `KlausFunctionalTests.cs`/`KlausInterruptTests.cs` (SixtyFiveXX) side by side.
- I did not read `sim6502-lsp` in depth beyond confirming (via grep) that it never
  imports `sim6502.Proc` — I'm reporting an absence, not a full read of that project.
- `MicroOpTable.cs`/`MicroOp.cs` (283 + 207 lines) were read only through what `Cpu.cs`
  references (`MicroOpTable.Mos6502`, `.ResetEntry`, `.IrqEntry`, `.Ops`, `.Entry`,
  `.Info`) — I did not verify there is no partial/experimental multi-variant table
  scaffolding already started inside `MicroOpTable.cs` itself; `Cpu.cs`'s hardcoded
  `_table = MicroOpTable.Mos6502` in the constructor is the definitive signal that
  variant selection isn't wired to `Cpu<TBus>` regardless, but the table-building code
  itself wasn't inspected for partial future-proofing.
