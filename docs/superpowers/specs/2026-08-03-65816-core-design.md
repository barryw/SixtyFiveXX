# SixtyFiveXX — the 65816

**Goal:** Take the engine from five certified 8-bit cores to six, the last of which has 16-bit registers,
24-bit addressing, two processor modes, two independently selectable register widths, and per-cycle pin
outputs the 8-bit parts do not have.

**Status:** design approved 2026-08-03.

**Scope:** `W65C816`. This spec sits under `docs/superpowers/specs/2026-07-31-sixtyfivexx-design.md`, whose
§5.4 already commits to *"its own opcode table on the **same** engine and the same tick loop"* and to
widening `CpuState` for every variant. Where the two disagree, the architecture spec governs.

**Documentary basis:** `docs/superpowers/research/2026-08-03-65816-reference-sources.md`. Every cycle
count, effective-address formula and wrapping rule below traces to a named source in that document. It is
a prerequisite read, not an appendix — §3 of it records two places where the most famous 65816 reference
is wrong, and a plan written from memory would have reproduced both.

## Established facts — verified, do not re-derive

From the research document, all confirmed by direct reading of the sources:

- **The vectors are a different repository.** `SingleStepTests/65816`, not the `65x02` set `HarteCache`
  fetches today. 512 files, `{opcode:x2}.e.json` and `{opcode:x2}.n.json`, 10,000 vectors each,
  **5,120,000 total, ~2.9 GB** on top of the ~3.8 GB the existing five cores need.
- **The JSON shape is different.** New state fields `dbr`, `pbr`, `d`, `e`; `a`/`x`/`y`/`s`/`d` are 16-bit;
  RAM addresses are 24-bit; each cycle carries an eight-character pin string `dpvremxl`.
- **Internal cycles perform no memory access.** The vector README is explicit: RAM is not activated unless
  VDA, VPA or VPB is asserted, and the value is recorded as `null`. Every 8-bit core in this project reads
  the bus on every cycle, because on those parts every cycle *is* an access. That stops being true here.
- **The per-cycle pin states are specified, not merely observed.** WDC datasheet Table 5-7 (pp. 36–42)
  gives VPB, MLB, VDA, VPA, address bus, data bus and RWB for every cycle of every addressing mode. The
  vectors assert exactly what that table specifies.
- **Indexed reads with 16-bit index registers pay their extra cycle unconditionally.** Datasheet Note 4
  (*"or write, or X=0"*) and Clark's `LDA abs,X` formula `6-m-x+x*p`, in which the page-cross term is
  multiplied by `x` and therefore vanishes at `x=0`. Eyes & Lichty's footnote 3 says only "if adding index
  crosses a page boundary" and is **wrong**; see research §3.2.
- **P register bit 4 is `x` in native mode and `b` in emulation mode; bit 5 is `m`.** Clark §4 and
  datasheet §2.8, agreeing with the 6502 layout this repository already implements. Eyes & Lichty p. 72
  places the break flag at bit 5 and is **wrong**; see research §3.1.
- **Direct-page page-wrapping requires `E == 1 && DL == $00`**, and the wrapped address keeps `DH`. Not
  `D == 0` — Clark's appendix is explicit that "the DH register need not be zero".
- **Exact cycle formulas exist for the whole phase 7b slice.** Research §5 tabulates all 15 addressing
  modes of `LDA` and `STA` from Clark §6.5, cross-checked against Table 5-7.

## Phase split

Six phases. The first extra one is the state widening, given its own phase for the same reason the
`ICpuVariant` refactor got one in phase 3: **it touches the hot path of cores that already pass millions
of vectors, and it adds no features, so its gate is the absence of change.** A regression that lands in
the same phase as 250 new opcodes is a regression nobody can attribute.

The second is the split of the original 7c, made once its real size was counted: 180 opcodes, against
7b's 32. The split is not by volume but by risk. 121 of those opcodes reuse the addressing engine 7b
certified and add nothing structural beyond the operand-width mechanism; the other 59 carry every new
mechanism left in the instruction set — Note 17's run-time read-modify-write direction, the accumulator
and implied forms, and transfers whose width comes from the destination register. Mixing them would bury
a defect in the second group inside 2.4 million vectors of routine work in the first, which is the same
argument that gave 7a its own phase.

| # | Deliverable | Gate |
| --- | --- | --- |
| **7a** | `CpuState` widening; `IBus.Internal` | **Zero behaviour change.** Every phase 1–6 suite green on both TFMs. No 65816 code at all. |
| **7b** (complete) | 65816 foundations: variant, 24-bit addressing, DP/DBR/PBR, M/X width plumbing, all 15 addressing modes, per-micro-op pin classification, the 65816 conformance harness | `LDA`/`STA` across all 15 modes, plus `XCE`/`REP`/`SEP` — 32 opcodes, `.e` and `.n`, **640,000 vectors**, full pin string asserted — verified, see §"Phase 7b" Gate |
| **7c** | Bulk ALU and the remaining loads, stores and compares — 121 opcodes, and the operand-width mechanism they all depend on | Those 121 opcodes' vectors, `.e` and `.n`, **2,420,000** |
| **7c′** | Read-modify-writes, shifts, accumulator and implied forms, transfers, `XBA`, flag instructions — 59 opcodes, and datasheet Note 17 | Those 59 opcodes' vectors, **1,180,000** |
| **7d** | Control flow, stack, interrupts (native vs emulation vectors), `MVN`/`MVP`, `COP`/`WDM`, `WAI`/`STP` | **All 512 files** — the full 5,120,000 |
| **7e** | 65816 disassembler and documentation | 64tass round-trip, as phase 6a |

Phase 7b's slice is chosen because `LDA` and `STA` between them use **every** 65816 addressing mode —
including all seven the 8-bit cores have never seen: `[dp]`, `[dp],Y`, `long`, `long,X`, `sr,S`,
`(sr,S),Y` and `(dp)`. The entire addressing engine is therefore forced into existence and certified
against real vectors before ~250 further opcodes are built on top of it. `XCE`/`REP`/`SEP` come along
because they are the only instructions that change `e`, `m` and `x`, and every invariant in 7b depends on
those transitions being right.

## Phase 7a — widening the state

### `CpuState`

```csharp
public struct CpuState
{
    public ushort PC;
    public ushort A;      // the full 16-bit accumulator
    public ushort X;
    public ushort Y;
    public ushort S;
    public ushort DP;     // the Direct register
    public byte P;
    public byte DBR;
    public byte PBR;
    public bool E;
}
```

The eight-bit cores use the low bytes and leave the rest alone. `TVariant.Variant` folds away every check
they never take, exactly as it already does for the 6510's port.

Two naming decisions, both forced:

- **`DP`, not `D`.** WDC and Clark both call the direct register `D`, but `CpuState.D` is already the
  decimal-mode flag property and has been since phase 1. `DP` is unambiguous and is the other name in
  common use.
- **`A` is the full 16 bits**, matching the vectors' `a` field. Clark calls this "the C accumulator" and
  reserves "A" for its low byte; that convention is noted in the XML docs so a reader holding Clark is not
  misled. Low/high accessors are not added until something needs them — `XBA` and the 8-bit paths, in 7c.

Flags gain the native-mode aliases:

```csharp
public const byte X = 0x10;   // index register width (native). Same bit as B.
public const byte M = 0x20;   // accumulator/memory width (native). Same bit as U.
```

Deliberately the *same* constants as `Flag.B` and `Flag.U` rather than new bits, because that is what the
silicon does — bit 4 is the break flag in emulation mode and the index-width select in native mode. Two
names for one bit is the honest encoding, and it puts research §3.1's finding somewhere a reader will
trip over it. `CpuState` gains `M` and `XFlag` properties (`X` being taken by the register).

`ToString()` prints `A`/`X`/`Y`/`S` as four hex digits and appends `DBR`/`PBR`/`DP`/`E` when any is
non-default. This changes output for the 8-bit cores, whose values will now print as `A:0042` rather than
`A:42`. No prior test asserted on `ToString()`, so `CpuStateTests` gains new tests for it rather than being
updated — additive coverage, not a test update. It is a debug string, and a mode-blind struct cannot know
how wide to print without being told.

### `IBus.Internal`

```csharp
public interface IBus
{
    byte Read(int address);
    void Write(int address, byte value);

    /// <summary>An internal-operation cycle: the core drives an address but performs no access.</summary>
    void Internal(int address) { }
}
```

A default implementation, so no existing bus breaks. **Both shipped buses implement it explicitly** —
`RefBus` forwards to its inner bus, and `FlatBus` implements it as an empty method rather than inheriting
the default. `FlatBus` has no side effects to suppress, so the body is empty either way; the point is that
an explicit implementation on a `struct` is a direct call, whereas inheriting the default is a constrained
call that boxes. `FlatBus` is the bus the README's examples use and the one a reader will first pair with
the 65816, so it must not be the one that allocates.

**The call is guarded by `TVariant.Variant == CpuVariant.W65C816`.** That is a compile-time constant per
closed generic type, so the five 8-bit cores do not merely skip the call — the JIT never emits it. This
matters more than it looks: a default interface method invoked on a `struct` type parameter that does not
override it is a constrained call that **boxes**, and a per-cycle allocation would destroy the performance
gate. Guarding on the variant removes the hazard from every core that exists today.

```
ponytail: a third-party struct bus used with the 65816 that does not implement Internal will box once per
internal cycle. Both shipped buses implement it, so this reaches nobody who has not written their own.
Upgrade path if it ever bites: promote Internal to a required interface member. Not done now because it
would break every 6502-only implementer to serve a case none of them hit.
```

### Gate

**Zero behaviour change.** Every phase 1–6 suite green on both TFMs — 7.66 M+ Harte vectors, Klaus
functional, Klaus interrupt, Klaus 65C02 extended, VICE `cpuport/test1`, and the full unit suite. Plus:

- `PublicSurfaceTests.ExpectedPublicTypes` is unchanged in 7a — no new public *type* appears here.
- The benchmark gate must still pass. §5.4 of the architecture spec deferred the "does the wider state
  cost the 8-bit cores anything" measurement to this phase; this is where it is answered, with the
  fallback (a separate `Cpu816`) still on the table if the answer is bad.

Deliberately **not** in 7a: any 65816 opcode, any new addressing mode, any variant behaviour, and — see
below — the pin classification.

**Moved out of 7a into 7b:** the per-micro-op pin classification. Nothing consumes it until the 65816
conformance harness exists, so in 7a it would be untested code, and 7a's entire justification is that
every line in it is covered by a gate that already runs.

**Plan:** `docs/superpowers/plans/2026-08-03-phase7a-state-widening.md`.

**Measured** (2026-08-04): **the widening costs nothing measurable, and the trade holds.**

Getting to that answer took a correction worth recording, because the first attempt produced a confident
wrong number. A single pre-widening run early in the session read 137.6 MHz. Measured against a
post-widening median of three runs — 112.3, 109.2, 110.0, median 110.0 MHz — that looked like a
reproducible 20% regression, and it was written up as one.

It was an artifact. The 137.6 MHz reading was taken on an idle machine before hours of test runs and
subagent work; every later sample was taken under load. Re-running the *pre-widening* code three times on
the same loaded machine gave 111.3, 113.1 and 117.4 MHz — median 113.1, not 137.6. Comparing one lucky
run against a median is not a measurement.

Interleaving the two builds run-for-run, to cancel machine drift, settles it:

| Pair | Pre-widening | Widened |
| --- | --- | --- |
| 1 | 110.0 MHz | 112.5 MHz |
| 2 | 106.5 MHz | 110.4 MHz |
| 3 | 110.0 MHz | 109.2 MHz |

The widened core is *faster* in two of three pairs. Across every run taken under comparable load the
medians are 110.7 MHz pre-widening and 110.2 MHz widened — a 0.4% gap inside a ±5% run-to-run spread,
which is to say no detectable difference at all. Throughput clears the 50 MHz floor by better than 2×.

The `Cpu816` fallback that §5.4 of the architecture spec held in reserve is **not** needed: one engine,
one tick loop, one register file serves all six cores at no measured cost. The lesson for later phases is
the methodological one — this project's throughput gate is contention-sensitive by design, which is why it
is excluded from CI, so any comparison it is used for must be interleaved against a rebuilt baseline
rather than against a figure recorded at some earlier, quieter moment.

## Phase 7b — the 65816 foundations

### The variant and its table

`W65C816Variant` in `SixtyFiveXX.Variants`, wired into `MicroOpTable.OpcodeTableFor`. It is a **new public
type**, so `PublicSurfaceTests.ExpectedPublicTypes` gains an entry — a deliberate edit, which is precisely
the design intent of that test.

`MicroOpTable`'s `Sequences` record — the NMOS/CMOS substitution table — **does not stretch to the
65816** and will not be made to. The 816 gets its own emitter. Two reasons, both structural rather than
stylistic: its addressing modes have no NMOS or CMOS counterpart to substitute into, and datasheet
Note 17 means its read-modify-write direction depends on `E` at *run* time, whereas every substitution in
`Sequences` is resolved once at table-build time. Bending the existing mechanism would put a runtime
branch on the per-cycle path, which is the one thing the whole type-parameter design exists to avoid.

### Addressing

The 15 modes, with the wrapping rules from research §7. Named here because each is a rule the 8-bit cores
do not have and every one of them is a place to get it silently wrong:

- **Direct page** is confined to bank 0 and wraps at the bank 0 boundary. It page-wraps *additionally*
  when `E == 1 && DL == $00`, keeping `DH` — so the wrapped address is `0 : DH : (LL + X) & $FF`.
- **The stack** is confined to bank 0. In emulation mode it wraps at the page 1 boundary, and `SH` is
  forced to `$01` — but only for "old" instructions. `sr,S` and `(sr,S),Y` are new modes and never wrap
  at a bank boundary under any circumstances.
- **`abs`, `abs,X`, `abs,Y`** take their bank from `DBR` and **carry into the next bank**. Clark §5.1.2:
  "Otherwise, wrapping does not occur at bank boundaries."
- **`long` and `long,X`** are 24-bit calculations, wrapping only at the 16 MB boundary, and never pay a
  page-cross penalty.
- **PC is confined to bank `K`** — it rolls `$FFFF → $0000` without touching `PBR`.

### Widths and the two conditional cycles

Both follow the idiom the engine already uses for the CMOS decimal-mode extra cycle: emit the slot
unconditionally and let the preceding micro-op skip it by advancing `_mpc`, as
`ReadPageCrossCmosArith` does today. No new mechanism, and the tick loop is untouched.

- **16-bit access** is a second micro-op. The low-byte micro-op runs the operation and ends the
  instruction when the width bit says 8; otherwise it falls through to the high-byte micro-op.
- **The direct-page penalty** (datasheet Note 2, Clark's `w`) is a slot the operand fetch skips when
  `DL == $00`.
- **The indexed-read penalty** is *not* the 6502's page-cross rule. Per research §3.2 it is taken
  unconditionally when `x = 0`, and only on a page cross when `x = 1`. Writes always take it.

Research §5's formula table is the acceptance criterion for this phase, opcode by opcode.

### Per-micro-op pin classification

Table 5-7 specifies VPB, MLB, VDA and VPA for every cycle. Each is a fixed property of the micro-op — a
read at PC asserts VPA, a read at the effective address asserts VDA, an opcode fetch asserts both — so it
is a static table, built exactly the way `MicroOps.IsWriteCycle` already is:

```csharp
[Flags]
internal enum BusPins : byte { None = 0, Vda = 1, Vpa = 2, Vpb = 4, Mlb = 8 }
```

**Watch the polarity.** `VPB` and `MLB` are active-low pins, so Table 5-7 shows `1` for the ordinary case
and `0` when they are asserted — a vector pull, or the locked cycles of a read-modify-write. The vectors'
pin string is the other way round: `v` and `l` mean *active*. These flags mean **asserted**, matching the
vectors, so reading Table 5-7 into them requires inverting those two columns and not the other two.

`Cpu` exposes the current cycle's pins and address as **`internal`** members. Every test project already
has `InternalsVisibleTo`, so the conformance harness can assert the full eight-character pin string at
**zero public API cost**. `E`, `M` and `X` in that string are status bits the harness reads from
`State`; `RWB` it already derives from the existing write classification.

This is the one place the design got stronger after the research: an earlier draft deferred pin assertion
to a later phase, on the assumption the pins were only observable rather than specified. Table 5-7 says
otherwise, so they are asserted from this phase onward and there is no stated gap.

### The conformance harness

`Harte816Cache`, `Harte816Case` and `Harte816Bus`, alongside the existing ones rather than bolted into
them — the repository, the file naming, the JSON shape and the per-cycle assertion all differ, and
`HarteCache`'s `set` parameter cannot express `.e`/`.n` file pairs. Caching, the
`SIXTYFIVEXX_HARTE_DIR` override and the gitignored cache directory work exactly as they do today.

Asserted per cycle: address, value, direction, whether the cycle accessed memory at all, and the full
`dpvremxl` pin string. Asserted per vector: the complete final register file including `DBR`, `PBR`, `DP`
and `E`, plus every named RAM byte.

### Gate

32 opcodes × 20,000 vectors = **640,000**, both modes, no exclusions and no declared gaps.

**Verified** (2026-08-04): the gate is met. All 32 opcodes' vector sets are green in both
modes — 640,000/640,000, no exclusions, no declared gaps — on both `net8.0` and `net10.0`.
The full conformance run (65816 vectors alongside the five 8-bit cores) is 1,374/1,374 on
both TFMs, of which 1,309 are the pre-existing 8-bit-core tests, unchanged. The unit suite is
486/486, including 11 discrimination tests for rules no SingleStepTests vector reaches —
bank-carry vs. bank-0-wrap at every DBR-relative/long-mode and stack-relative `$xxFFFF`
boundary, the direct-page indirect pointer's own page-wrap condition in emulation mode,
`(dp),Y`'s indexing-cycle skip selected at table-build time rather than by opcode, and
`sr,S`'s missing direct-page penalty — each verified to fail against a deliberately broken
version of the corresponding production line before being restored. (The task 5, 6 and 7
reports that recorded the individual failure output live under `.superpowers/sdd/`, which is
gitignored and so not available to a reader of this repository; the summary above is what
survives.)

Phase 7b is complete. `LDA`/`STA` across all fifteen addressing modes, plus `XCE`/`REP`/`SEP`,
is 32 of the 65816's 256 opcodes; every other opcode still throws `UndefinedOpcodeException`.
Phases 7c, 7c′ and 7d add the remaining 224.

## Phase 7c — the bulk ALU, and the operand-width mechanism

**Status:** design approved 2026-08-05. Not started.

### What is in it, and where it stops

121 opcodes:

| Group | Opcodes |
| --- | --- |
| `ADC` `AND` `CMP` `EOR` `ORA` `SBC`, fifteen addressing modes each | 90 |
| `BIT` — `#`, `dp`, `dp,X`, `abs`, `abs,X` | 5 |
| `LDX` `LDY` | 5 each |
| `STX` `STY` | 3 each |
| `STZ` | 4 |
| `CPX` `CPY` | 3 each |

Every addressing mode here is one phase 7b already certified, with a single exception: **`dp,Y`**, used
by `LDX` and `STX` and by nothing else in the instruction set. It gets a new `AddrMode.DirectPageY`
rather than reusing the eight-bit cores' `ZeroPageY`, matching the decision 7b already made in keeping
`DirectPage` distinct from `ZeroPage` — the wrapping rules differ, and sharing a member would put an
`E`/`DL` test inside a micro-op the eight-bit cores also reach.

Deliberately **not** in 7c, and named so the boundary is not a matter of inference: no control flow, no
stack instruction, no read-modify-write, no transfer, no accumulator or implied form. Those are 7c′ and
7d. Nothing in this phase's 121 opcodes reaches any of the four carry-forward items 7b recorded — the
`~Flag.B` masking in `PullP`, the micro-ops still computing a bare sixteen-bit `PC`, `RmwMiddle`'s
`Unimplemented816`, or the 65816 IRQ sequence's stack mutation ahead of its throw — so all four stay
untouched here and remain 7c′/7d work.

### The width mechanism

Phase 7b hard-codes `_s.M` as the width test. That was correct while `LDA` and `STA` were the only
opcodes with an operand, and it stops being correct at `LDX`: the index loads, stores and compares take
their width from `x`, not `m`.

The test appears at exactly five sites, and it is worth naming them, because the count is smaller than
the eight-member access group suggests. Three micro-ops decide the width — `ReadExec816`,
`ExecWrite816` and `ImmExec816` — each by ending the instruction early when the width is eight. The
five high-byte micro-ops (`ReadExecHigh816`, `ExecWriteHigh816`, `ImmExecHigh816` and the two
bank-carrying variants) carry no test at all: they run only because the low-byte micro-op *did not*
end the instruction. The remaining two sites are `Exec`'s `Op.Lda` and `Op.Sta` arms.

`OpcodeInfo` gains a fifth parameter with a default, so all five eight-bit tables and every existing
call site compile untouched:

```csharp
internal enum Width : byte { None, M, X }

internal readonly record struct OpcodeInfo(
    string Mnemonic, AddrMode Mode, Op Operation, Access Access, Width Width = Width.None);
```

`Cpu` gains `private bool _wide`, assigned once per instruction in `FetchOpcode` inside the
variant-guarded block that already forces `SH`, `m` and `x` in emulation mode. The five eight-bit cores
never emit the assignment, so `_wide` is permanently `false` for them. The three deciding micro-ops then
test `!_wide` where they tested `_s.M`; the five high-byte micro-ops are untouched, since they never
tested anything.

**The variant guard must be kept in `Exec`, not replaced by `_wide`.** `Exec`'s `Op.Lda` and `Op.Sta`
arms read `TVariant.Variant != CpuVariant.W65C816 || _s.M` today, which folds to `if (true)` on every
eight-bit core and costs nothing. Rewriting that as a bare `!_wide` would put a field load on the 6502's
hottest path to serve a case the 6502 cannot reach. The correct form keeps the guard and swaps only the
second operand: `TVariant.Variant != CpuVariant.W65C816 || !_wide`.

Two properties of this design are stated here rather than left to be discovered:

- **Width is latched at fetch, not sampled per cycle.** Nothing in 7c can change `m` or `x` part-way
  through an instruction, so the distinction is unobservable in this phase. It becomes observable in 7d,
  when `PLP` and `RTI` can rewrite `P` mid-sequence, and latching is the behaviour a decoder that
  resolves width once actually has. Documented on `_wide` itself, so 7d inherits the reasoning rather
  than re-deriving it.
- **`Width.None` is a real value, not a placeholder.** `XCE`, `REP` and `SEP` have no operand width, and
  neither will most of 7d. An opcode carrying `Width.None` that reaches an access micro-op is a table
  bug, and the retrofit task adds the assertion that says so.

### Sixteen-bit operation semantics

`SetZN16` already exists from 7b. Widening `AND`, `ORA`, `EOR`, the compares, `BIT` and binary
`ADC`/`SBC` is mechanical: `N` from bit 15, `Z` across all sixteen bits, carry from bit 16, overflow
from bit 15. `BIT`'s immediate form still sets only `Z` — the behaviour this repository already models
as `Op.BitImm` for the 65C02 — while its other modes take `N` from bit 15 and `V` from bit 14 when
`m = 0`.

**Decimal-mode `ADC`/`SBC` at sixteen bits is the open question of this phase, and it is answered from
the sources before any opcode is written.** This repository already carries `Op.AdcCmos`/`Op.SbcCmos` as
members separate from `Op.Adc`/`Op.Sbc` precisely because the CMOS parts changed decimal flag behaviour,
and phase 2a's ledger records that the separation was necessary rather than tidy. The same question is
open again for the 65816 and is not assumed away.

Task 1 is therefore research-only and produces a new §10 in
`docs/superpowers/research/2026-08-03-65816-reference-sources.md`, settling four things from Clark and
the datasheet:

1. Which of `N`, `V` and `Z` derive from the corrected BCD result and which from the binary
   intermediate, at sixteen bits. Phase 1's NMOS answer does not transfer.
2. Whether the 65816 can reuse `Op.AdcCmos`/`Op.SbcCmos` or needs a third pair. **The rule is
   pre-committed: reuse only if the sources state the behaviour is identical; any divergence, or any
   silence, gets its own members.** Not "reuse and let the vectors object".
3. Table 5-7's `Direct,Y` row, transcribed in §9's format.
4. That `LDX #`, `LDY #`, `CPX #` and `CPY #` are `3-x` cycles and `3-x` bytes, mirroring `LDA #`'s
   `3-m`. Near-certain, transcribed regardless — 7b's 280,000 vectors green on the first run came from
   transcribing Table 5-7 before writing code, and that is the practice being repeated, not a formality.
5. Clark's cycle formula for every one of the 121 opcodes, and with it the one question that changes the
   shape of the `ADC`/`SBC` task rather than only its arithmetic: **does the 65816 pay an extra cycle in
   decimal mode?** The 65C02 does, which is why `MicroOp.BcdExtra` and the conditionally-skipped slot in
   `MicroOpTable.EmitAccess` exist in this codebase at all. If the 65816's formula carries no decimal
   term, `ADC` is an ordinary read and the emitter is untouched; if it does, the task adds a skipped slot
   and a new micro-op to classify. Settled from the formula table before the task starts, not discovered
   from a cycle-count mismatch 600,000 vectors in.

already certified, so a fault in `_wide`'s `X` path surfaces on a compare rather than entangled with
sixteen-bit BCD.

`ADC` and `SBC` are one task rather than a binary task and a decimal one, because they cannot be split
by gate: a single `.n` file mixes vectors with `D` set and clear, so there is no subset of the vectors
that certifies binary arithmetic alone.

Task 3 also carries two structural edits. `EmitLdaSta816` stops being `LDA`/`STA`-specific and becomes
the general 65816 addressing emitter; its `default:` throw stays, since it is the tripwire that catches
an addressing mode with no sequence. And `Exec`'s width branches move behind `_wide` in the form given
above.

### Gate

**All 121 opcodes green in both `.e` and `.n`, no exclusions and no declared gaps** — 2,420,000
vectors, holding phase 7b's bar rather than relaxing it for volume. Each task additionally re-runs every
previously certified vector: the 1,309 eight-bit conformance tests and everything earlier in the phase.

`Harte816Tests.ExpectedImplementedOpcodes` is bumped once per task — 32 → 77 → 98 → 128 → 133 → 153 —
so an opcode dropped from the table shrinks the run and fails loudly rather than passing quietly. It is
one of the two tripwires 7b left in place for exactly this phase.

This phase adds **no public API surface**. `OpcodeInfo`, `Width`, `AddrMode` and `Op` are all `internal`,
and `PublicSurfaceTests.ExpectedPublicTypes` is unchanged.

## Public API changes

All breaking, all in one release, all deliberate. The package is at 0.1.0 and its only intended consumer —
sim6502 — has not yet swapped, so the cost of breaking now is the lowest it will ever be.

| Change | Effect |
| --- | --- |
| `CpuState.A`/`X`/`Y`/`S` widen to `ushort` | `byte v = cpu.State.A;` no longer compiles |
| `CpuState` gains `DP`, `DBR`, `PBR`, `E`, `M`, `XFlag` | Additive |
| `Flag` gains `M` and `X` | Additive; aliases of `U` and `B` |
| `CpuState.ToString()` format | Wider fields, plus a conditional 65816 tail |
| `IBus.Internal(int)` | Additive, defaulted; `RefBus` forwards |
| `W65C816Variant` | New public type (7b) |

## Risks

- **The widening is the highest-risk change here, and it adds no features.** It touches the hot path of
  five cores certified against millions of vectors, and its gate is the absence of change — harder to
  reason about than any new assertion. This is exactly why it is phase 7a alone. The specific hazard is
  arithmetic that previously truncated silently at 8 bits and now does not.
- **The wider struct may cost the 8-bit cores.** The architecture spec deferred this measurement to this
  phase and named the fallback: a separate `Cpu816` over the same building blocks. 7a answers it before
  anything is built on top.
- **+2.9 GB of vectors**, taking a full conformance run to ~6.7 GB and roughly doubling its runtime. May
  force a per-variant CI stage, as the 65C02 sets already nearly did.
- **The book is wrong twice, and it is the reference most people reach for.** Research §3 records both
  findings with their evidence, so that a future contributor "correcting" the code toward Eyes & Lichty
  finds the argument before they find the diff.
- **Note 17's runtime-dependent RMW direction** is the first behaviour in this project that cannot be
  resolved at table-build time. It lands in 7c′, but it constrained 7b's emitter design, which is why the
  816 got its own emitter then rather than after the problem appeared.
- **The RDY halt path drives `_addr`**, whose staleness is already a recorded limitation in `Cpu.Tick`.
  On a 24-bit address that limitation is wider, not different. Unchanged in scope; noted so it is not
  mistaken for new.

## Out of scope

- **ABORT (`ABORTB`) and datasheet Note 3.** No vectors exercise it. Out of scope for phase 7 entirely.
- **Eyes & Lichty Appendix E**, a reprint of the 1986 data sheet, superseded by the 2024 revision.
- **The performance pass** — phase 8 in the architecture spec, deliberately after every core exists.
- **Machine personalities**, including any 65816 machine. Phase 9.
- **The disassembler's `m`/`x` problem**: immediate operand width is not statically knowable, so
  `Decode` needs explicit flags. Phase 7e, and it does not constrain anything before it.
